## 2. 最後に観測した環境の詳細

### VM 152（テスト側）

- `/usr/local/etc/rc.d/cpansmoker` は **停止保護付き版**（[参考スクリプト](scripts/cpansmoker-guarded)）をインストール済み。元の版は `cpansmoker.before-guarded-stop` にバックアップ。
- `/usr/local/libexec/cpansmoker-run` は固定ターゲットなしで CPAN 全体を走査。rc.d の監視コマンドは `daemon -f -H -R 60`、`cpansmoker_enable=YES`。
- `/usr/local/etc/newsyslog.conf.d/cpansmoker.conf` の 10 MiB / 7世代ローテーションは **実動作検証済み**。SIGHUP によるログの再オープンと、以後の新ログへの継続書き込みを確認。
- `qm shutdown 152 --timeout 240 --forceStop 0` による正常停止後、VM 起動時に **手動 `onestart` なし**で自動復帰。観測時 supervisor PID **1396** / Smoker PID **1397**、新しい `t/xs/*.t` テスト出力あり。PID は過去の値です。
- 最初の内訳スナップショットは通常領域 **PASS 177 / FAIL 1 / UNKNOWN 3 / NA 0**、`reports/hold` に **PASS 3**。その後、通常領域 PASS の **サイズ調査では 268件**（32 KiB 以下146件、32–256 KiB 122件、256 KiB 超0件）。**継続稼働により件数は変わる**ため、固定値として扱わないこと。
- `/home/cpansmoke/reports/hold/` 内の3件は **転送対象外**。その他のレポートも自動的に全送信しない。

**停止処理の未解決問題：** `service cpansmoker onestop` は改良版で **最大90秒・失敗時 exitcode 1・自動 SIGKILL なし**を実証。ただし依存テスト Attean が子プロセスとして孤立（PPID=1）し、supervisor が `piperd` で終了しなかった。`fstat` により、supervisor のログ読み取り FD と孤立 Attean の標準出力 FD が **同一パイプの両端**と確認。後に孤立 Attean に手動 SIGTERM を送り、全プロセスの消滅を確認して安全に一つだけ再起動できた。**rc.d 単独の正常停止が自動で成立するとは未検証**。

### VM 151（送信側）

- `/home/cpansend/{incoming,inflight,sent}` を使う。`/home/cpansend/send-batch.pl` を使用（`.broken` 旧版は使用しない）。
- `send-batch.pl` は `inflight` があれば停止、同名レポート拒否、`incoming → inflight → sent` の順で移動。送信前に `Test::Reporter` で内容を確認。**PASS のみ**、`File-Marker-0.14` は除外、**15.1-release-p6** の subject を要求。`incoming` が空でも非ゼロ終了するため、cron の単純起動に不向き。
- `/home/cpansend/.cpanreporter/metabase_id.json` は存在し権限 0600。**内容を表示・コミットしない**。
- VM 151 には `/usr/local/bin/sudo` が **ない**。`/usr/bin/su -m cpansend -c 'HOME=/home/cpansend /usr/local/bin/perl /home/cpansend/send-batch.pl'` が動作実証済み。
- 送信に失敗したか成功したか不明なら **`inflight` を自動再送しない**。重複投稿の可能性があるため手動確認。
- `cpansend` / `cpansmoke` / root の crontab は確認時未設定。自動転送・投稿の稼働実績はない。

## 3. 現在のブロッカー：Guest Agent がデータ転送で応答不能になる

ネットワーク：ホスト `vmbr1=10.151.0.1/24` ↔ VM 151 `10.151.0.2`、`vmbr2=10.152.0.1/24` ↔ VM 152 `10.152.0.2`。VM 151→152 の TCP/22 接続は失敗。ホスト→両 VM の TCP/22 も **`nc -n -z -v -w 3` で Connection timed out**。`ip route get` ではホストから各 VM への直結ルートあり、`pve-firewall status` は `disabled/stopped`、`net.ipv4.ip_forward=1`、VM の `qm config net0` に `firewall=1` 表示なし。**SSH の失敗原因は未特定**。ホスト転送が有効なので、**2 VM が安全に隔離されているとは未検証**。不用意にファイアウォールを解除しない。

転送実験の結果：

| 方法 | 結果 |
| --- | --- |
| Guest Agent `file-read` → `file-write`、`/etc/shells` 154 bytes | 読み戻し完全一致で成功 |
| `file-write` で DBI .rpt 19,063 bytes を一括書き込み | **タイムアウト**。VM 151 の `qemu-ga` が応答不能となり、一時ファイルは **0 bytes** |
| `file-write` 1,024 bytes | 成功、読み戻し一致 |
| `qm guest exec 151 --pass-stdin` 512 bytes | 成功 |
| 同コマンドで **1,024 bytes × 19 回**、DBI .rptを転送 | **成功**。VM 151 側の SHA-256 一致 |
| 同コマンドで **8,192 bytes** のダミーデータを一括入力 | **タイムアウト**し、**再び Guest Agent が応答不能**。対象一時ファイルは見つからず |

**最後の観測**：8 KiB 失敗後に VM 151 のコンソールで `service qemu-guest-agent onestatus` は **PID 2558** で稼働、`ps` では `select` 待ちだったが、**ホスト側の `qm guest cmd 151 ping` は応答不能**。その後の Guest Agent 再起動・疎通回復の成功結果はまだ受け取っていない。したがって、**「復旧済み」と記録しない**。VM 151 自体は稼働し、シリアルコンソールから操作できた。

**判断：Guest Agent に大きな一括転送を繰り返さない。1 KiB 転送の成功実績はあるが、無人運転での安定性は未証明。** 将来の定期転送は、セキュリティ境界を保った **Proxmox ホストから各ゲストへの必要最小限の SSH/SCP** 等を検討する。認証情報は VM 151 のみに置き、VM 152 に Proxmox ホスト鍵や送信側の秘密を入れない。

## 4. 次回の開始手順（まず読み取り専用）

以下は **Proxmox ホスト `root@pve`** で実行。最初から再転送・自動送信しない。

~~~sh
echo '=== VM status ==='
qm status 151
qm status 152

echo '=== VM 151 QGA (bounded) ==='
timeout 12 qm guest cmd 151 ping
echo "qga exitcode=$?"

echo '=== VM 152 smoker ==='
timeout 15 qm guest exec 152 -- /usr/sbin/service cpansmoker onestatus
~~~

VM 151 の Agent が応答しなければ、Proxmox ホストで `qm terminal 151`（**Ctrl+O で終了**）。FreeBSD root で次を確認。必要なら **VM 再起動ではなく Agent のみ**を再起動し、ホスト側で `qm guest cmd 151 ping` を再確認：

~~~sh
service qemu-guest-agent onestatus
ps -axo pid,stat,wchan,command | grep '[q]emu-ga'
# 状態を確認した後にのみ、必要なら：
service qemu-guest-agent restart
~~~

続いて Proxmox ホストで **設定を変更せず**通信を調査：

~~~sh
for ip in 10.151.0.2 10.152.0.2; do
  echo "=== $ip ==="
  ping -c 2 -W 2 "$ip" || :
  ip neigh show to "$ip"
  timeout 5 nc -n -z -v -w 3 "$ip" 22 || :
done
bridge link show
ip -4 route get 10.151.0.2
ip -4 route get 10.152.0.2
pve-firewall status
~~~

VM 151 の FreeBSD 側（`qm terminal 151`）で：

~~~sh
service sshd onestatus
sockstat -4 -l | grep ':22' || :
ifconfig vtnet0
netstat -rn -f inet
ping -c 2 10.151.0.1
~~~

VM 152 の SSH 側も必要に応じて読み取り専用で確認。ARP/ICMP/SSH のどの段階で途切れるか確認し、**ホスト↔ゲストの経路だけを許可する最小設定**を検討する。現状 `ip_forward=1` のため VM 152→VM 151 の遮断も明示的に検証する。

VM 151 の Agent が復旧した場合だけ、キューの状態を再確認：

~~~sh
qm guest exec 151 -- /bin/sh -c '
  for d in incoming inflight sent; do
    printf "%s: " "$d"
    find "/home/cpansend/$d" -maxdepth 1 -type f -name "*.rpt" | wc -l
  done
'
~~~

## 5. 自動化を進める順序・安全条件

1. **先にネットワーク原因を診断**。VM 間を直接通信させず、ホスト経由で安定転送できることと隔離を確認する。Guest Agent の大容量転送は再実験しない。
2. **転送のみ**を少数（まず1件）対象として実装・検証。VM 152 の `reports/` の直下だけ対象、`hold/` は除外。**完全転送→サイズと SHA-256 検証→内容の検証→一時ファイルから `incoming` へ原子的配置**。途中失敗時は公開キューへ入れない。
3. **重複判定はファイル名だけに依存しない**。時刻・PID の異なる同一ディストリビューション／結果／環境のテストがあり、`sent` に同名がないだけでは未送信とは限らない。既存20件と今後の送信履歴を保護する。
4. **送信は別プロセス**で検証後に定期実行を有効化。送信結果不明の `inflight` は自動リトライ不可。最初は PASS/15.1-release-p6 に限定されていることに注意し、FAIL/UNKNOWN/NA 対応は別途仕様を決める。
5. cron/スケジューラ、排他ロック、件数上限、失敗時の通知・ログ・リトライ規則・ディスク管理を整え、段階的に無人運転へ移す。

**避ける操作：** 過去の `sent` を削除・再送、`hold` を一括送信、`inflight` の自動再送、Agent 不応答時に大量の Guest Agent コマンドを投入、SSH 接続のため VM 間の制限を無検証で解除、Smoker を転送作業のために停止。
